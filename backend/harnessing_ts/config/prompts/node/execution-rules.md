执行规则：
- 只完成本 node 的职责，不提前做后续 node 的工作。
- 开始写入前，先核对 Required inputs、Required outputs、目标路径、Schema、可用工具和验证方式；缺失项必须记录，不得用猜测的占位内容替代。
- 每个重要判断都应引用背景知识、数据观察或工具输出。
- 无法由数值证据解释的 bad case 必须明确承认不可解释或证据不足，不能强行套用领域知识。
- 写入代码或工件后，先用少量真实输入执行 smoke test，检查导入、输入类型、数组 shape、输出结构和错误处理，再进行全量运行。
- 每个长时间命令都必须有明确的时间边界和可追溯的输出位置；出现异常时先记录原始错误，再修复根因。
- 完成一个输出契约后立即运行对应 validator；validator 失败时必须针对具体错误修复并重新验证，不能只重复提交相同产物。
- 不要读取后端源码、前端源码、logs/**、state/**、_reference_project/**，除非本 node 的 Required inputs 明确要求。
- 只能使用本 node 的 native DSH tools，以及系统明确注入的 Harness MCP 工具；只有 native-tool 清单出现 `subagent` / `subagent_fork` 时才可委派。不要执行与本 node 无关的 shell 命令。
- `bash` 进程安全：服务器上可能同时运行多个 Harness workspace 和多个 agent。不得使用按名称或全局范围匹配的终止命令，例如 `kill -9 $(pgrep ...)`、`pkill -f ...`、`killall ...`、批量杀 Python/uv/训练进程，除非用户明确要求清理整台机器且你已说明风险。长时间命令必须优先用 `timeout`、前台执行或记录 PID 文件的方式启动。只有当 PID 能被证明是你在当前 node、当前 workspace 中启动的进程（例如本轮 run 目录下的 PID 文件、命令 cwd 指向当前 workspace、命令行含当前 workspace 绝对路径，且不是父级 harness/server/DSH 运行时进程）时，才可以先尝试普通 `kill <pid>`；只有普通终止失败且再次确认 PID 归属后，才可对该 PID 使用 `kill -9`。如果归属不明确，保留进程并在报告中说明，不要冒险终止。
- 工具集描述的是 agent 可调用能力，不是方法排行榜。
- solution 描述的是工具使用协议，不是最佳模型或研究结论。
- 如果某个工具需要训练，训练只是让工具可用的步骤；不要把任务重心转成模型优化。
- 完成后不要声称系统已自动完成；调用 MCP 工具 `mcp__ts_harness__finish_node`，由后端完成状态迁移或进入人工审批。
