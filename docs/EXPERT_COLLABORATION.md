# Expert collaboration in the ICDE demo

## Patient-visible interaction focus

The patient surface avoids repeated identity disclaimers while retaining specific unresolved facts and clinically relevant actions. New responses may include `contextUpdates` (exact user quote + explanation focus); server validation checks the quote against actual user input, never report/assistant text. This is a model explanation of its response focus, not evidence of diagnostic/treatment change. Generic questions may return no updates. Task cards additionally expose only completed, application-recorded material checks. No original report, model score or saved task is rewritten, and no clinical validation is claimed.

## Presentation scope: current case and tuning set

The demo UI now shows tuning-only counts, F1, attempts, change links and expert report summaries. Holdout and combined totals are omitted from rendering, including the scripted synthetic scene. Tuning regressions remain visible; the displayed scope explicitly says it is not independent generalization validation. Backend splits, evaluation computation, stored metrics and report histories remain unchanged. Source and API audit data continue to retain the full evaluation.

## Scripted positive interaction scene

`/demo?scenario=positive` mounts a separate, explicitly synthetic presentation. Both groups improve under its narrow scripted criterion; counts and F1 are calculated from disclosed SIM records. The broad round preserves its simulated regressions. The terms tuning/holdout here denote presentation groups, not independent validation. All Agent text and report wording are scripted and labeled; no model call, real record access or publication occurs. Original stored feedback, metrics and reports remain in the real-data workspace. Do not use these synthetic outcomes as research evidence.

## Patient answer quality and evidence boundary

Demo report explanation, investigation follow-up and the legacy `/question` adapter share a patient-only projection of published materials. Legacy research comparisons are omitted without rewriting originals; informative measurement sentences remain available for interpretation, with plain-language output enforced separately. Quick topic buttons only prepare drafts; sending remains explicit. Old reports/outputs, prediction records and the root workbench remain unchanged. Prompt and narrow lexical checks are not clinical factuality validation.

## Observation-driven agent mode (2026-10-19)

The expert UI defaults to **Agent-led investigation**. Submit a review goal rather than operate each tool. The agent selects its next allowlisted check from actual measurements and earlier tool observations, then may stop or ask a focused question about unavailable information. This is a bounded tool-use loop, not a predetermined animation. The visible action receipt includes short action justifications, factual observations and the stop reason; it is not hidden chain-of-thought. A maximum of three checks, no duplicate action/focus and a 150-second total deadline bound cost and latency. Every provider/tool await is guarded by context, report and collaboration versions before further action; a failed investigation saves no successful round or report.

When a scalar candidate is supported, the application automatically runs boundary tests and real measurements on the current case plus up to seven of the user's selected cases, then asks the model to reconsider its recommendation against that replay. The assessment can retain the candidate for review, withhold recommendation, or ask an essential expert question. It cannot silently widen bounds, declare accuracy gains, adopt or publish. A withheld recommendation remains inspectable; any override requires the same explicit expert adoption. Auto-replay receipts have the same adoption/version checks as manual validation. Editing or rerunning invalidates the previous model assessment; manual replay is not silently followed by a second model call. The initial draft and proposal are explicitly labeled as preceding the replay; the separate assessment is the post-replay advice.

The agent does not select a representative cohort, interpret morphology, validate source quotations, search literature, modify its own code or learn model weights. Comparison cases are the user's selection, not autonomous discovery. Existing single-check API clients remain compatible: send `autonomous: true`, `action: "auto"` and optional `caseIds` (up to eight) to opt in. The UI opts in by default. Explicit single-check actions keep the previous behavior. New code is scoped to `agent_investigation.py`; prompts are `investigate-next.md` and `assess-replay.md`.

## Expert-informed revision loop (2026-10-19)

The primary feedback workspace sends an opinion to `POST /api/demo/{dataset}/cases/{id}/revision`. A bounded agent (`revision_loop.py`, prompt `revise-next.md`) searches a **closed candidate space** and the application evaluates every candidate deterministically. The result is a separate expert-informed demo assessment beside the immutable original prediction, not a clinical diagnosis. No automatic publication occurs; an adopted result can be explicitly linked to a separately saved/published report with `revisionItemId`.

Candidate space: a decision threshold for one class (`threshold`), or a conjunction of one to three numeric conditions that adds or removes one label (`criterion`). A condition tests either a flattened extractor measurement column (for example `qrs_duration_ms.qrs_ms`) or the classifier probability of a class. Candidates are validated by schema and against the real column and class names; no generated code is executed. A missing measurement makes a feature condition not assessable and keeps the original decision. When the available columns cannot express the opinion, the agent returns `cannot_express` and names the missing measurement instead of approximating.

Data and evaluation: the latest completed iteration's validation probabilities and frozen per-class thresholds, the dataset labels, and a precomputed extractor feature table (`state/revision-loop/val-features.json`, built offline with `python -m harnessing_ts.revision_loop build --workspace <workspace>`; 2193 records took about 70 s with four workers). Loading refuses to run unless the recomputed baseline equals `metrics_formal.json` (per-class TP/FP/FN/TN and macro F1) and the table matches the current iteration and extractor fingerprint. The validation fold is split by patient into a **tuning set** and a **holdout set**. The agent sees only tuning-set numbers (at most three evaluations, one more call to finish, 150 s total). The application reports both sets to the expert. The holdout set is reported as a separate audit, not proof of generalization after repeated expert feedback; the reviewed patient is excluded when necessary. The test fold is not used. "Now agree" and "no longer agree" count records whose decision for the target class changes relative to the dataset label, which is a weak label. The verdict is mechanical: improved only if the record count and the target-class F1 move the same way, otherwise mixed. A change that fixes the focus case but loses on the holdout set is shown as such.

Storage and decisions: saved under `revisions` in the existing context-bound record, with its own revision counter, beside reviews and collaboration. Items preserve `parentId` and optional `sourceReportRevision`. Only the latest pending item can be adopted/rejected. Adoption records a version, `changesPredictions: false` and `published: false`. Report creation accepts only an adopted item with current input fingerprint and report lineage; under the record lock the server creates an immutable `feedbackImpact` snapshot from the saved candidate, focus before/after, evaluations and opinion, never trusting browser-supplied impact data. Patient views and Q&A receive only that published snapshot, never the mutable revisions collection or unpublished results. A case keeps at most 20 revisions. Failures and conflicts save nothing and retain the browser draft.

Cache safety: compute the extractor content version and SHA-256 of the feature table, validation probabilities, metrics and metadata BEFORE looking up the process cache, including same-mtime rewrites. Rehash after loading to reject concurrent changes. Guard every provider await and adoption/report linking against the current fingerprint. An unavailable/stale table on a decision/link is a recoverable 409. Feature-table builds reject extractor/iteration changes during extraction. No stale result is silently adopted.

Evaluation limits: if the focus case belongs to the holdout half, exclude its entire patient from the holdout cohort (`reviewN`) because the agent sees its truth and measurements. All-validation summaries may still contain that patient and are not unseen evidence. Follow-up history contains tuning statistics only. Repeated expert feedback after inspecting holdout results is NOT an independent clinical validation. The bounded implementation changes thresholds or numeric criteria, not model architecture/training or unsupported morphology.

Limits: model output varies between runs, so the same opinion can end in different candidates. Most simple rules do not improve this classifier; "the evidence does not support your opinion" is an expected, valid result. Records without usable measurements are not assessable for feature conditions.

# Context-aware patient loop

`patient_context.py` distinguishes locally explicit denials from reported/uncertain mentions; this is a bounded lexical aid, not a clinical risk classifier. Both `/understand` and the task route use the shared urgent gate. Denied lists no longer become emergencies merely because of keywords; mixed/uncertain urgent symptoms remain conservative. Only user turns contribute to `patientContext.symptoms`; exact quote and turn provenance are retained. Report comparison uses the actual published revision/labels, never a dataset label, model score or the patient's recollection. An explicit normal/abnormal claim conflicting with that snapshot is surfaced, without claiming diagnostic verification.

The optional `followUpQuestion` asks one useful missing question TO the patient while giving practical guidance now. It is distinct from patient-to-Agent `nextQuestion` and system evidence-target `reviewQuestion`. Personal context in prepare mode requires a nonempty follow-up with one bounded rewrite. UI **Add my answer** only prepares editable text; it never auto-submits or changes a report. Prior responses remain historical. Later context can change the explanatory hypothesis without changing diagnosis/treatment. Tests cover denials, contrast scopes, English/Chinese, report conflicts, and two-turn refinement. Language models and bounded lexical patterns are not clinically validated.
